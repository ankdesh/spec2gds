Release with evidence

A release is ready after all packages pass.

Uploading one package is not enough. A profile may need many matching packages. Promotion marks the complete, verified set as available for applications.

  1. Build Harness from a clean source commit.
  2. Pack only the selected modules. Record each archive checksum.
  3. Install the declared consumer dependencies through a candidate registry.
  4. Build spec2gds, then check clean web and headless installations and assembled releases.
  5. Run the required application test profiles against the candidate packages. Missing model credentials or failed checks stop publication.
  6. Publish those exact archive bytes to GitHub Packages.
  7. Verify every published checksum, then create the release receipt.

What happens if publishing stops?

The release is not promoted. A retry can reuse a package version only when its registry checksum matches the tested archive. A conflicting version stops the release.

A local candidate with uncommitted Harness changes cannot be published by this pipeline.

How does spec2gds upgrade?

The release includes a small archive with test reports, size measurements, and the tested development and production locks. The release receipt records their checksums, so an upgrade can check that the locks are the tested files.

A developer adopts the promoted release and its tested development and production locks. The developer runs the application checks and reviews the dependency update. Existing installations keep their old locks until that update is accepted.

node scripts/adopt-harness-release.mjs \
  PROMOTED_RELEASE_DIRECTORY VERIFIED_CONSUMER_DIRECTORY
npm run build
npm test

Routine installation then uses npm ci. The ci command uses the committed lock. It reports a failure if the package declarations and lock do not agree.

Who needs which access?

ActionAccess
Install a private releasePackage read access.
Build and test candidate archivesSource read access. No package write token.
Publish tested archivesPackage write access in the separate publishing job.
Change Harness sourceA developer checkout, selected explicitly for source development.

The first publication needs GitHub configuration: package access for spec2gds, a read token for a private consumer checkout, and the package-release environment. The local implementation does not create those account settings.
