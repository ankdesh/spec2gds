# Deterministic SystemC AT Activity

`systemc.generate_at_skeleton` generates the first structural phase of a
SystemC TLM 2.0 Approximately-Timed performance model. The Activity is entirely
deterministic: it does not call an LLM, interpret narrative text, generate
traffic, or infer performance behavior.

## Input and topology

The Activity must be invoked on one selected design. It uses the high-level
Spec API for target identity, dependency selection, and provenance, then uses
the immutable low-level IR for instances, compositions, interface roles, and
connection endpoints.

Generation follows the selected design's reachable component-composition
hierarchy. It supports:

- one initiator-to-one target TLM interface connections;
- initiator and target interface roles;
- same-role SystemC hierarchical socket exports for composite boundaries; and
- unused component interfaces, which are omitted from the instance-specialized
  generated module.

The availability check rejects the complete launch before writing files when
it finds ad-hoc connections, system or monitor roles on used connections,
fan-in, fan-out, ambiguous boundaries, or another unsupported endpoint shape.
Diagnostics include every unsupported reachable connection found during
preflight.

## Generated project

The caller supplies a `LocalActivityWorkspace` rooted at the repository's
`generated/` directory. The Activity publishes:

```text
generated/systemc-at/<document-id>/<design-id>/
├── CMakeLists.txt
├── README.md
├── generation-manifest.json
├── include/
│   ├── components/          # instance-specialized leaf modules
│   └── designs/             # composite modules and selected top
└── src/main.cpp
```

Each used target socket returns `END_REQ` one 10 ns cycle after `BEGIN_REQ`.
Initiator sockets accept backward phase updates. The generated top owns all
instances and bindings; `sc_main` constructs it and runs an empty 100 ns
simulation. Phase one intentionally has no PEQs, payload generation,
forwarding, VCD signals, or functional behavior.

The ownership manifest records the generator, source revision, selected design,
and hashes of generated files. Rerunning atomically replaces the stable folder
only when the existing manifest identifies the same generator, document, and
design. Unmanaged folders and symbolic links are refused.

## Code-generation templates

Generated C++, CMake, and project documentation are rendered from packaged
Jinja2 templates under
`spec2gds/agent_spec/activities/systemc_at/templates/`. The Python generator
retains every semantic decision: Spec traversal, topology validation, name
allocation, socket direction, connection ordering, and manifest hashing.
Templates receive only normalized strings, booleans, and ordered collections
and are responsible only for text layout.

The Jinja environment uses `StrictUndefined`, disables autoescaping, fixes
newlines to `\n`, preserves the trailing newline, and applies explicit block
whitespace controls. Input collections are ordered in Python before rendering.
Templates must not read Spec objects, timestamps, environment variables,
random values, or filesystem state. These constraints keep generated bytes and
reports repeatable for an identical source snapshot.

## Invoke from Python

```python
from pathlib import Path

from spec2gds.agent_spec.activities import (
    ActivitySnapshot,
    LocalActivityWorkspace,
    SpecExtensionRegistry,
    invoke_activity,
)
from spec2gds.agent_spec.activities.systemc_at import register_extensions
from spec2gds.agent_spec.spec_format.ir import SpecRevision

revision = SpecRevision.load("design.spec")
target = revision.entry_designs()[0].ref
snapshot = ActivitySnapshot.create(revision, target)

registry = SpecExtensionRegistry()
register_extensions(registry)
result = invoke_activity(
    registry,
    "systemc.generate_at_skeleton",
    snapshot,
    LocalActivityWorkspace(Path("generated")),
)
print(result.summary)
```

The result contains a typed report and a `generation-report.json` artifact.
Both record the workspace-relative path, source revision, selected design,
module and connection counts, complete file inventory, and deterministic tree
digest. The generated C++ project itself is the managed workspace output, not
an Activity artifact.

## Build and verify

Generated projects require C++17 and a SystemC 2.3.3 installation exporting the
`SystemCLanguage` CMake package:

```bash
cmake -S generated/systemc-at/<document-id>/<design-id> \
  -B /tmp/systemc-at-build \
  -DCMAKE_PREFIX_PATH=/path/to/systemc-dist
cmake --build /tmp/systemc-at-build
```

Repository tests always verify deterministic generation. To additionally
compile and run the generated fixture, set `SYSTEMC_PREFIX`:

```bash
SYSTEMC_PREFIX=/path/to/systemc-dist \
  uv run python -m pytest tests/agent_spec/activities/systemc_at -q
```
